# Illustration render

An illustration here is an HTML block that is designed like a web page, screenshotted at 2x, finished with a rounded border and saved as lossless WebP. Rendering from HTML keeps the real fonts, lets one source produce a light and a dark image from the same markup, and makes every later edit a text edit plus one command.

Every repository gets its own signature: a vector shape language, a typeface and a way of presenting, derived from what the project is. This skill ships no look. The contract between a source page and the renderer, the quality floor and the method for finding the signature live in `frontdoor-core`; this skill adds how to draw scenes and diagrams (`references/scene-craft.md`). Two repositories that use it must not end up with one design and different text.

## The core

`<core>` is the folder `frontdoor-core` beside the folder this file sits in (`<skill-dir>/../frontdoor-core`). Before step 1, check that `<core>/SKILL.md` exists. When it is missing, stop and tell the user to install it with `npx skills add https://github.com/the-khiem7/frontdoor.git --skill frontdoor-core`; never do its steps from memory. Read `<core>/SKILL.md`: its principles hold for every step below. `fd` below is the harness that `<core>/references/harness.md` lists, run from inside the repository: `uvx python -I <core>/scripts/fd.py` for the board and `fd contrast`, and `uvx --from playwright --with pillow python -I <core>/scripts/fd.py` for `fd render`, `fd animate` and `fd daemon`.

## Workflow

1. **Find the brand.** Read the repo's logo, banner, existing CSS or docs site, app theme tokens, and its README tone. When the evidence disagrees (the code's theme is one blue, the icon and screenshots are teal), pick the one visitors actually see, which is usually the icon and the screenshots, and say which you chose. If a signature already exists in the repo (source pages with a signature note, a hero), continue it instead of inventing another.
2. **Find the signature.** If the caller (for example `frontdoor-readme`) handed you a signature, or the repo's source pages already carry a signature note, use it and go to step 3. Otherwise, with no brand evidence or a brand that leaves the drawing style open, follow `<core>/references/signature.md` and write the six-line signature note. For a new repository, or when asked for a fresh look, show rough directions (one hero each, low fidelity) on the design board and let the user choose or mix, run as `<core>/references/board.md` says: the board page is the caller's page, or the use case of the pictures (`readme`, `landing-page`, `product`, or a slug of your own for other work), added with `fd page add <page>` when `fd status` does not list it; ask the user how many directions to make, with a recommendation; `fd round new <page> --count <N>`; build each direction in its folder with its own inline CSS and any font specimen, render it into its `out/`, and `fd round add <page>`. Nothing in `.frontdoor/` is committed. With no user to answer, make 3, write the question with that answer to `questions.md`, pick the strongest yourself, record it with `fd choose`, and write the reason to `questions.md`. Ask the user for a direction only when the repo gives you nothing to derive one from.
3. **Set up the source folder.** Before choosing it, check which folders the repo's linter, formatter, docs site and Docker context cover: sources placed where a linter runs get linted in CI, and files in a docs site's public folder are published. Pick `assets/source/` or the folder the repo already uses, or one that those tools ignore. Copy `<core>/assets/starter.css` to `shared.css` and `<core>/assets/shared.js` to `shared.js`, then replace the tokens and the font with the signature's, add the shapes it needs, and delete the `--starter-placeholder` line. Start each source page from `<core>/assets/starter.html` and put the signature note in its header comment.
4. **Build one `.item` per image.** Each `.item` has a unique `id`, because `fd render` names the file after the id, and sets its own size: a README picture is 1200 CSS px wide. Write each source page's header comment with the exact render command so the next person can repeat it. Choose a scene or a diagram per picture with `references/scene-craft.md`. The contract, the quality floor and the craft notes are in `<core>/references/source-page.md`.
5. **Render.** Run
   ```
   uvx --from playwright --with pillow python -I <core>/scripts/fd.py render <page.html> --root <assets dir> --out <assets dir>
   ```
   `--root` is the folder served over HTTP; it must contain the source page, `shared.css` and `shared.js`, and the folder the output goes to. With sources in `assets/source/` and images in `assets/`, use `--root assets --out assets`. `--items a,b` renders a subset, `--themes light` skips the dark pair, and `--watch` renders again on every save. When you render more than a few times, run `fd daemon start` first so one browser stays open. It uses Edge or Chrome already on the machine, so nothing is downloaded and no admin rights are needed. It exits 1 and prints a WARN when content leaves an item's box, a file is over `--max-kb` (default 300), a font was requested but did not load, or the starter placeholder is still served. It prints the fonts and grounds it found; copy them into the signature note. It checks the item's own box, not a card or node inside it, so a label that runs out of its card passes silently: look at every image. A shape meant to run off the edge goes inside an element marked `data-bleed`.
6. **Look at every image.** Open each WebP with the image viewer you have, light and dark. The renderer cannot judge whether a picture reads well or whether text is cramped. Compute the contrast of the smallest text pairs in both themes with `fd contrast <fg> <bg> [...]`. Run the swap test from `<core>/references/signature.md`. Fix the source and render again.
7. **Moving picture.** When the user wants a picture that moves (the README banner), render the frames from the same source page with `fd animate`, the one tool for animation. The output is a looping animated WebP, never a GIF. The page exposes a function of one value, the harness calls it for every frame, and the motions, `--draft` and `--batch` are explained in the docstring of `<core>/scripts/animate.py`.
8. **Report** the files written with their sizes, the signature in its six lines, and anything not checked (for example, how the page looks on the hosting site).

## Choosing how to take the screenshot

`fd render` is the default because it needs no MCP server and writes anywhere. If the user prefers a browser MCP, the same contract holds: serve the folder, open `<page>?theme=light|dark`, screenshot each `.item` at CSS scale, then run the finishing step of the renderer (`finish_and_save` in `<core>/scripts/fdlib/render.py`) on the PNG. Some browser tools only write inside the repo root, so keep intermediates in a temporary folder there and delete it afterward.

## Pitfalls that cost time before

- A page opened as a plain file has no `?theme=` and no relative-path server, so fonts and `../logo.png` can fail. Always render through `fd render`, which serves the folder over HTTP.
- Web fonts load from the network. Render online; `fd render` warns when a requested font did not load and a fallback face is in the images. A repository that uses system fonts has the opposite problem: the fonts must be installed on the machine that renders, and a different machine will render different images. Load only open-license families from a font host, or the repository's own fonts; never copy a font file into the skill or the repo without its license.
- Do not stop to ask when nobody can answer (an automated run, a test): take the recommended default, write each question with the answer you assumed to the caller's `questions.md`, or to one at the repository root, and go on.
- Text inside an image cannot be selected or searched. Every illustration that carries information needs an `alt` text that says the same thing in words; the frontdoor-readme skill covers how.
- Do not commit the intermediate PNGs. Only the `.webp` files, the still PNG of a `data-social` item and the HTML sources belong in the repo.
